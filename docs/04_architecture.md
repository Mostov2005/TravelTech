# Архитектура системы TravelTech

## 1. Общая архитектура системы

TravelTech построена на основе микросервисной архитектуры. Система состоит из пяти микросервисов, каждый из которых отвечает за отдельную область предметной деятельности (Bounded Context).

### 1.1. Состав микросервисов

**Identity Service**
- Регистрация пользователей.
- Аутентификация и авторизация.
- Управление учётными записями.
- Выдача JWT-токенов.

**Trip Service**
- Создание и управление путешествиями.
- Формирование и изменение маршрутов.
- Управление бронированиями.
- Кэширование данных путешествий.

**Flight Service**
- Хранение информации об авиарейсах.
- Хранение информации об аэропортах.
- Предоставление информации о рейсах.
- Синхронное взаимодействие с Flight Monitoring Service через gRPC.

**Flight Monitoring Service**
- Управление мониторингом авиарейсов.
- Хранение текущих статусов рейсов.
- Обработка изменений статусов.
- Предоставление информации о мониторинге другим компонентам.

**Recovery Service**
- Обработка нарушений расписания.
- Координация процесса восстановления путешествий.
- Формирование предложений по изменению маршрутов.
- Выполнение компенсирующих действий при ошибках распределённой операции.

### 1.2. Инфраструктурные компоненты

Помимо микросервисов, система использует следующие компоненты:

- **PostgreSQL** — хранение данных микросервисов.
- **Redis** — кэширование данных Trip Service.
- **RabbitMQ** — асинхронный обмен сообщениями.
- **Docker** — контейнеризация приложений.
- **Docker Compose** — запуск и управление компонентами системы.

Внешние запросы направляются непосредственно к REST API соответствующих микросервисов. Отдельный API Gateway в текущей реализации не используется.

## 2. Организация хранения данных

Для хранения данных применяется подход Database per Service: каждый микросервис самостоятельно управляет собственной базой данных.

Используются следующие базы данных PostgreSQL:

| Микросервис | База данных |
|---|---|
| Identity Service | identity_db |
| Trip Service | trip_db |
| Flight Service | flight_db |
| Flight Monitoring Service | monitoring_db |
| Recovery Service | recovery_db |

На этапе разработки все базы размещаются в одном экземпляре PostgreSQL, но логически разделены.

Каждый микросервис работает только со своей базой данных. Прямой доступ к таблицам других микросервисов не используется. Для обмена информацией применяются REST API, gRPC и асинхронные сообщения RabbitMQ.

## 3. Взаимодействие микросервисов

В системе используются три основных механизма взаимодействия.

### 3.1. REST API

Для взаимодействия с клиентами и выполнения операций между микросервисами используется REST API на базе FastAPI.

Каждый микросервис предоставляет собственные HTTP-эндпоинты и Swagger UI.

### 3.2. gRPC

Для синхронного взаимодействия Flight Service и Flight Monitoring Service используется gRPC.

Описание контракта взаимодействия хранится в файле `flight.proto`. На его основе используются сгенерированные Python-классы клиента и сервера.

### 3.3. RabbitMQ

Для асинхронного обмена сообщениями используется RabbitMQ.

Взаимодействие реализовано с применением Transactional Outbox: бизнес-изменение и соответствующее событие сначала сохраняются в одной транзакции базы данных. Затем отдельный процесс публикует событие в RabbitMQ.

Это позволяет избежать ситуации, когда бизнес-данные сохранены, но событие для других компонентов не отправлено.

## 4. Внутренняя архитектура микросервисов

При разработке микросервисов используются принципы Clean Architecture. Код разделён по ответственности на несколько логических компонентов.

### 4.1. API Layer

Реализован с использованием FastAPI.

Отвечает за:
- обработку HTTP-запросов;
- проверку входных данных;
- вызов бизнес-операций;
- формирование HTTP-ответов.

Основные файлы: `api.py`, `schemas.py`.

### 4.2. Service Layer

Содержит сценарии использования и координирует выполнение бизнес-операций.

Например, Trip Service выполняет создание, получение и изменение путешествий.

Основной файл: `services.py`.

### 4.3. Domain Layer

Содержит элементы предметной области и бизнес-правила.

В зависимости от микросервиса включает:
- доменные сущности;
- бизнес-логику;
- правила обработки операций.

Основной файл: `domain.py` (в тех микросервисах, где он используется).

### 4.4. Data Access Layer

Отвечает за взаимодействие с базой данных.

Включает:
- модели SQLAlchemy;
- реализацию репозиториев;
- операции чтения и записи данных.

Основные файлы: `models.py`, `repositories.py`, `database.py`.

Такое разделение позволяет отделить обработку запросов и бизнес-логику от деталей хранения данных.

## 5. Распределённые механизмы

### 5.1. Saga Orchestration

Для координации распределённых операций в Recovery Service применяется паттерн Saga Orchestration.

Recovery Service выступает оркестратором и управляет последовательностью действий в нескольких микросервисах.

Если один из этапов завершается ошибкой, выполняется компенсирующее действие для отмены ранее выполненных изменений.

Такой подход позволяет управлять распределёнными операциями без использования общей транзакции между несколькими базами данных.

### 5.2. Transactional Outbox

Для надёжной публикации событий используется паттерн Transactional Outbox.

В рамках одной транзакции:
1. Сохраняются изменения бизнес-данных.
2. В таблицу Outbox записывается событие.
3. После успешного завершения транзакции отдельный процесс получает событие из Outbox.
4. Событие публикуется в RabbitMQ.

Таким образом, сохранение бизнес-данных и запись события выполняются атомарно.

### 5.3. Кэширование Redis

Redis используется в Trip Service для кэширования данных.

При повторном обращении к кэшируемым данным сервис может получить результат из Redis, не выполняя дополнительный запрос к PostgreSQL.

## 6. Аутентификация и авторизация

Для централизованной аутентификации используется Identity Service.

После успешной аутентификации сервис выдаёт JWT-токен. Другие микросервисы используют этот токен для проверки доступа к защищённым эндпоинтам.

Для подписания и проверки токенов используется алгоритм HS256.

## 7. Контейнеризация и запуск

Каждый микросервис имеет собственный Dockerfile и файл зависимостей `requirements.txt`.

Для совместного запуска компонентов используется Docker Compose.

В состав инфраструктуры входят:
- пять микросервисов;
- PostgreSQL;
- Redis;
- RabbitMQ.

Конфигурация запуска находится в корневом файле `docker-compose.yml`.

## 8. Итог

Архитектура TravelTech обеспечивает независимость микросервисов, разделение данных по ограниченным контекстам и взаимодействие с использованием REST, gRPC и RabbitMQ.

Распределённые бизнес-операции координируются с помощью Saga Orchestration, а для надёжной публикации событий применяется Transactional Outbox.
