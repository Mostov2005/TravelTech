# Architecture

## 1. Общая архитектура системы

TravelTech разрабатывается на основе микросервисной архитектуры.

Система состоит из пяти основных микросервисов, каждый из которых отвечает за отдельный Bounded Context предметной области.

### 1.1. Состав микросервисов

**Identity Service**
- Регистрация и авторизация пользователей.
- Управление учётными записями и ролями.
- Выдача и обновление JWT-токенов.

**Trip Service**
- Управление путешествиями.
- Формирование и изменение маршрутов.
- Хранение информации о бронированиях.

**Flight Service**
- Хранение информации об авиарейсах.
- Хранение информации об аэропортах.
- Предоставление сведений о рейсах другим сервисам.

**Monitoring Service**
- Запуск и управление мониторингом рейсов.
- Получение обновлений из внешних источников.
- Обнаружение задержек и отмен.
- Сохранение истории изменений статусов.

**Recovery Service**
- Обработка нарушений расписания.
- Определение затронутых путешествий.
- Поиск альтернативных рейсов.
- Формирование предложений по корректировке путешествий.
- Отправка уведомлений пользователям.

### 1.2. Инфраструктурные компоненты

Помимо микросервисов, система включает следующие компоненты:

- **API Gateway** — единая точка входа для внешних запросов и их маршрутизация к микросервисам.
- **PostgreSQL** — основная система хранения данных.
- **Redis** — кеширование часто используемых данных и хранение временной информации.
- **RabbitMQ** — асинхронный обмен сообщениями между микросервисами.
- **Docker Compose** — запуск и управление всеми компонентами системы.

## 2. Организация хранения данных

Каждый микросервис владеет собственными данными и самостоятельно управляет своей базой данных.

Для реализации подхода Database per Service используются отдельные базы данных PostgreSQL:

- identity_db;
- trip_db;
- flight_db;
- monitoring_db;
- recovery_db.

На этапе разработки базы данных могут размещаться в одном экземпляре PostgreSQL, но каждый микросервис получает доступ только к собственной базе.

Прямой доступ одного микросервиса к таблицам другого микросервиса не допускается. Для обмена информацией используются API и асинхронные сообщения.

## 3. Взаимодействие компонентов

Для синхронного взаимодействия между микросервисами используются REST и gRPC.

Для асинхронного обмена командами и событиями используется RabbitMQ.

API Gateway принимает внешние запросы и направляет их соответствующим микросервисам.

Каждый микросервис содержит собственную бизнес-логику и отвечает за целостность своих данных.

## 4. Внутренняя архитектура микросервисов

Для организации внутренней структуры каждого микросервиса используется Clean Architecture.

Архитектура разделяет приложение на четыре основных слоя.

### 4.1. Presentation Layer

Отвечает за взаимодействие с внешними клиентами.

Основные задачи:
- обработка HTTP-запросов;
- валидация входящих данных;
- формирование HTTP-ответов;
- передача запросов в Application Layer.

В качестве основного инструмента используется FastAPI.

### 4.2. Application Layer

Содержит сценарии использования (Use Cases), которые реализуют операции приложения.

Например, в Trip Service:
- CreateTrip;
- GetTrip;
- UpdateTrip;
- CancelTrip.

Application Layer координирует выполнение операций и обращается к необходимым интерфейсам.

### 4.3. Domain Layer

Содержит основную бизнес-логику приложения.

Включает:
- сущности и агрегаты;
- объекты-значения (Value Objects);
- бизнес-правила и ограничения.

Domain Layer не зависит от фреймворков, баз данных и других внешних технологий.

### 4.4. Infrastructure Layer

Отвечает за взаимодействие с внешними техническими компонентами.

Включает:
- реализацию репозиториев с использованием SQLAlchemy;
- подключение к PostgreSQL;
- взаимодействие с Redis;
- отправку и получение сообщений через RabbitMQ;
- интеграцию с внешними системами.

### 4.5. Принципы взаимодействия слоёв

Внутренние слои не должны зависеть от внешних технических компонентов.

Application Layer обращается к интерфейсам, а Infrastructure Layer предоставляет их конкретную реализацию.

Такое разделение позволяет изменять используемые технологии без существенного изменения бизнес-логики.
