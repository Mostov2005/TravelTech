# Бизнес-процессы системы TravelTech

## 1. Регистрация и аутентификация пользователей

**Участник:** пользователь, Identity Service.

**Описание:** создание учётной записи и получение доступа к системе с использованием JWT.

**Последовательность действий:**
1. Пользователь отправляет данные для регистрации.
2. Identity Service проверяет введённые данные.
3. Сервис создаёт учётную запись и связывает её с ролью.
4. Пользователь отправляет данные для входа.
5. Identity Service проверяет учётные данные и выдаёт JWT-токен.
6. При необходимости пользователь обновляет токен с помощью refresh-токена или завершает сессию.

**Результат:** пользователь получает токен для доступа к защищённым функциям системы.

## 2. Управление путешествиями

**Участник:** пользователь, Trip Service.

**Описание:** создание и управление путешествиями пользователя.

**Последовательность действий:**
1. Пользователь отправляет запрос на создание путешествия.
2. Trip Service проверяет данные и сохраняет путешествие.
3. Пользователь может получить список своих путешествий.
4. При необходимости пользователь изменяет данные или удаляет путешествие.

**Результат:** в системе хранится информация о путешествиях пользователя.

## 3. Формирование маршрута

**Участник:** пользователь, Trip Service.

**Описание:** добавление и управление сегментами маршрута внутри путешествия.

**Последовательность действий:**
1. Пользователь выбирает путешествие.
2. Добавляет сегмент маршрута.
3. Указывает идентификатор рейса, аэропорты отправления и прибытия, время вылета и прилёта.
4. Trip Service сохраняет сегмент и связывает его с путешествием.
5. Пользователь может просматривать и изменять состав маршрута.

**Результат:** путешествие содержит последовательность сегментов маршрута.

## 4. Управление бронированиями

**Участник:** пользователь, Trip Service.

**Описание:** хранение и управление информацией о бронированиях, связанных с путешествием.

**Последовательность действий:**
1. Пользователь добавляет бронирование.
2. Указывает идентификатор рейса, номер бронирования и при необходимости номер билета.
3. Trip Service сохраняет бронирование и связывает его с путешествием.
4. Пользователь может просматривать, изменять и удалять информацию о бронировании.

**Результат:** в системе хранится информация о бронированиях пользователя.

**Примечание:** TravelTech хранит информацию о бронированиях, но не выполняет реальные платежи и не покупает авиабилеты.

## 5. Управление информацией об авиарейсах

**Участник:** внутренние сервисы системы, Flight Service.

**Описание:** хранение и предоставление информации об аэропортах и авиарейсах.

**Последовательность действий:**
1. В Flight Service добавляются сведения об аэропортах.
2. Сервис сохраняет данные аэропортов, включая IATA-код, название, город и страну.
3. Добавляются сведения об авиарейсах: номер, авиакомпания, аэропорты и время вылета и прилёта.
4. Другие сервисы получают информацию о рейсах через API Flight Service.

**Результат:** система располагает централизованной информацией об аэропортах и авиарейсах.

## 6. Мониторинг авиарейсов

**Участник:** Flight Service, Flight Monitoring Service.

**Описание:** создание записей мониторинга и хранение текущих статусов рейсов с историей их изменений.

**Последовательность действий:**
1. Flight Monitoring Service получает запрос на создание записи мониторинга рейса.
2. Сервис сохраняет идентификатор рейса и его начальный статус.
3. При изменении статуса создаётся новая запись в истории статусов.
4. Flight Service взаимодействует с Flight Monitoring Service по gRPC для выполнения соответствующих операций.
5. Сервис предоставляет информацию о текущем статусе и истории изменений.

**Результат:** в системе хранится информация о состоянии рейсов и история изменения их статусов.

## 7. Обработка нарушений авиасообщения

**Участник:** Recovery Service, Trip Service, Flight Service.

**Описание:** регистрация проблем, связанных с нарушениями в авиасообщении.

**Последовательность действий:**
1. Recovery Service получает запрос на регистрацию нарушения.
2. Сохраняет идентификаторы затронутого путешествия и рейса.
3. Указывает тип нарушения, описание и начальный статус обращения.
4. При необходимости сервис получает связанные данные из других микросервисов.

**Результат:** в системе зарегистрирован случай нарушения, который может быть обработан в рамках процесса восстановления путешествия.

## 8. Восстановление маршрута (Saga Orchestration)

**Участник:** Recovery Service, Trip Service, Flight Service.

**Описание:** координация процесса восстановления путешествия с использованием паттерна Saga Orchestration.

**Последовательность действий:**
1. Recovery Service начинает процесс обработки нарушения.
2. Получает необходимые данные о путешествии и рейсе от соответствующих сервисов.
3. Формирует предложение по использованию альтернативного рейса.
4. Сохраняет предложение в Rebooking Proposals.
5. При выполнении операции изменения путешествия обращается к Trip Service.
6. Если операция завершается ошибкой, Recovery Service выполняет предусмотренные компенсирующие действия.
7. Состояние процесса обновляется в соответствии с результатом выполнения операций.

**Результат:** процесс восстановления маршрута координируется Recovery Service, а результаты операций сохраняются в соответствующих базах данных.

**Примечание:** система не выполняет реальное перебронирование у авиакомпании и не покупает билеты.

## 9. Асинхронный обмен событиями

**Участник:** Trip Service, RabbitMQ, сервисы-получатели событий.

**Описание:** передача событий между микросервисами с использованием Transactional Outbox и RabbitMQ.

**Последовательность действий:**
1. Trip Service выполняет операцию изменения данных.
2. В рамках одной транзакции сохраняет изменения и соответствующее событие в таблице Outbox.
3. Компонент публикации получает необработанные события.
4. События отправляются в RabbitMQ.
5. Сервис-получатель получает сообщение и обрабатывает его.
6. После успешной публикации событие отмечается как обработанное.

**Результат:** микросервисы могут обмениваться событиями без необходимости выполнять синхронные вызовы для каждой операции.

## 10. Кэширование данных

**Участник:** Trip Service, Redis.

**Описание:** использование Redis для ускорения доступа к часто запрашиваемым данным.

**Последовательность действий:**
1. Trip Service получает запрос на чтение данных.
2. Сервис проверяет наличие данных в Redis.
3. Если данные найдены, возвращает их из кэша.
4. Если данных нет, получает их из PostgreSQL и сохраняет в Redis.
5. При изменении данных кэш обновляется или инвалидируется.

**Результат:** сокращается количество обращений к PostgreSQL при повторном чтении кэшируемых данных.
