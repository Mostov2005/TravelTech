# DDD Design

## 1. Bounded Contexts

В системе TravelTech выделены следующие ограниченные контексты:

1. **Identity** — управление пользователями и авторизацией.
2. **Trip Management** — управление путешествиями, маршрутами и бронированиями.
3. **Flight Information** — хранение и предоставление информации об авиарейсах и аэропортах.
4. **Flight Monitoring** — мониторинг рейсов и обнаружение изменений их статусов.
5. **Travel Recovery** — обработка проблем с рейсами и подготовка предложений по корректировке путешествий.

Контекст 	Агрегаты
Identity	User, Role, RefreshSession
Trip Management	Trip, Itinerary, Booking
Flight Information	Airport, Flight
Flight Monitoring	FlightMonitoring, FlightStatus (кандидат)
Travel Recovery	DisruptionCase, RebookingProposal


## 2. Identity Context

**Назначение:** управление учётными записями пользователей, аутентификацией, ролями и сессиями авторизации.

### 2.1. Агрегаты

**User**
- Идентификатор пользователя.
- Email.
- Хеш пароля.
- Статус учётной записи.
- Дата регистрации.

Основные операции: регистрация, изменение данных, изменение пароля, блокировка и разблокировка.

**Role**
- Идентификатор роли.
- Название.
- Список разрешений.

Основные операции: создание роли, изменение разрешений, удаление роли.

**RefreshSession**
- Идентификатор сессии.
- Идентификатор пользователя.
- Хеш refresh-токена.
- Срок действия.
- Дата отзыва.

Основные операции: создание сессии, обновление токена, отзыв сессии.

### 2.2. Бизнес-правила

- Email пользователя должен быть уникальным.
- Пароли хранятся только в виде хеша.
- Пользователь должен иметь назначенную роль.
- Нельзя использовать отозванную или просроченную refresh-сессию.
- Заблокированный пользователь не может проходить авторизацию.

## 3. Trip Management Context

**Назначение:** управление путешествиями пользователей, их маршрутами и информацией о бронированиях.

### 3.1. Агрегат Trip

**Trip** представляет отдельное путешествие пользователя.

Основные данные:
- Идентификатор путешествия.
- Идентификатор владельца.
- Название.
- Дата начала.
- Дата окончания.
- Статус.
- Дата создания.

Основные операции:
- создание путешествия;
- изменение названия и дат;
- отмена путешествия;
- завершение путешествия.

Бизнес-правила:
- Дата окончания не может быть раньше даты начала.
- У каждого путешествия должен быть владелец.
- Завершённое путешествие нельзя редактировать без специальной операции повторного открытия.

### 3.2. Агрегат Itinerary

**Itinerary** представляет маршрут путешествия и содержит последовательность этапов перемещения.

Основные данные:
- Идентификатор маршрута.
- Идентификатор путешествия.
- Список этапов маршрута.
- Дата последнего изменения.

Этап маршрута (Segment) содержит:
- Аэропорт отправления.
- Аэропорт прибытия.
- Дату и время отправления.
- Дату и время прибытия.
- Идентификатор авиарейса, если этап выполняется самолётом.

Основные операции:
- создание маршрута;
- добавление этапа;
- изменение этапа;
- удаление этапа;
- изменение порядка этапов.

Бизнес-правила:
- Маршрут должен быть связан с существующим путешествием.
- Аэропорты отправления и прибытия не должны совпадать.
- Время прибытия должно быть позже времени отправления.
- Этапы должны располагаться в логическом порядке.
- Последовательные этапы должны быть связаны по месту прибытия и отправления.

**Segment** является частью агрегата Itinerary и не представляет собой самостоятельный агрегат.

### 3.3. Агрегат Booking

**Booking** представляет информацию о бронировании авиабилета, связанном с путешествием пользователя.

Основные данные:
- Идентификатор бронирования.
- Идентификатор путешествия.
- Идентификатор авиарейса.
- Код бронирования.
- Номер билета (при наличии).
- Статус бронирования.
- Дата создания.

Основные операции:
- добавление бронирования;
- изменение информации о бронировании;
- изменение статуса;
- удаление бронирования.

Бизнес-правила:
- Бронирование должно быть связано с существующим путешествием.
- У бронирования должен быть указан авиарейс.
- Бронирование нельзя считать подтверждённым без соответствующего подтверждения.
- Отменённое бронирование нельзя использовать как действующее.

TravelTech хранит информацию о бронированиях, но не выполняет покупку билетов и оплату.

## 4. Flight Information Context

**Назначение:** хранение и предоставление информации об авиарейсах и аэропортах.

### 4.1. Агрегат Airport

**Airport** представляет аэропорт, используемый при описании авиарейсов и построении маршрутов.

Основные данные:
- Идентификатор аэропорта.
- Код IATA.
- Код ICAO.
- Название.
- Город.
- Страна.
- Часовой пояс.

Основные операции:
- добавление аэропорта;
- обновление информации;
- получение информации по идентификатору или коду.

Бизнес-правила:
- Код IATA должен быть уникальным, если он указан.
- Код ICAO должен быть уникальным, если он указан.
- У аэропорта должно быть название.
- Часовой пояс должен быть корректным.

### 4.2. Агрегат Flight

**Flight** представляет информацию о конкретном авиарейсе.

Основные данные:
- Идентификатор рейса.
- Номер рейса.
- Авиакомпания.
- Идентификатор аэропорта отправления.
- Идентификатор аэропорта прибытия.
- Плановое время отправления.
- Плановое время прибытия.

Основные операции:
- добавление информации о рейсе;
- обновление планового расписания;
- получение информации о рейсе;
- поиск рейсов по номеру, аэропортам и дате.

Бизнес-правила:
- У рейса должны быть указаны аэропорты отправления и прибытия.
- Аэропорты отправления и прибытия должны различаться.
- Время прибытия должно быть позже времени отправления.
- Рейс должен иметь номер и авиакомпанию.

Flight хранит идентификаторы аэропортов, а не сами объекты Airport.

## 5. Flight Monitoring Context

**Назначение:** автоматическое отслеживание авиарейсов, получение обновлений из внешних источников и обнаружение изменений их статусов.

### 5.1. Агрегат FlightMonitoring

**FlightMonitoring** представляет процесс наблюдения за конкретным авиарейсом.

Основные данные:
- Идентификатор мониторинга.
- Идентификатор авиарейса.
- Статус мониторинга.
- Время последней проверки.
- Время следующей проверки.
- Дата создания.

Основные операции:
- запуск мониторинга;
- приостановка мониторинга;
- возобновление мониторинга;
- завершение мониторинга;
- обновление времени последней проверки.

Бизнес-правила:
- Для одного процесса наблюдения не должно существовать нескольких активных записей мониторинга одного рейса.
- Завершённый мониторинг нельзя возобновить без специальной операции.
- Время следующей проверки должно быть корректным.

### 5.2. Агрегат-кандидат FlightStatus

**FlightStatus** представляет информацию о состоянии авиарейса, полученную в определённый момент времени.

Основные данные:
- Идентификатор записи.
- Идентификатор авиарейса.
- Статус рейса.
- Продолжительность задержки в минутах.
- Фактическое время отправления.
- Фактическое время прибытия.
- Время получения информации.

Основные операции:
- регистрация нового статуса;
- получение текущего статуса;
- получение истории изменений;
- сравнение нового статуса с предыдущим.

Бизнес-правила:
- Каждая запись должна быть связана с конкретным авиарейсом.
- У записи должно быть время получения информации.
- История изменений не должна перезаписываться при получении нового статуса.
- Повторное получение одинаковых данных не должно приводить к повторной обработке одного

## 6. Travel Recovery Context

**Назначение:** обработка нарушений расписания авиарейсов, оценка их влияния на путешествия и подготовка предложений по корректировке маршрутов.

### 6.1. Агрегат DisruptionCase

**DisruptionCase** представляет случай нарушения первоначального плана путешествия, например задержку или отмену авиарейса.

Основные данные:
- Идентификатор случая.
- Идентификатор затронутого путешествия.
- Идентификатор проблемного авиарейса.
- Тип нарушения.
- Описание проблемы.
- Статус обработки.
- Дата создания.

Основные операции:
- создание случая нарушения;
- изменение статуса;
- получение информации о проблеме;
- закрытие случая.

Бизнес-правила:
- Проблема должна быть связана с конкретным путешествием.
- Проблема должна иметь тип нарушения.
- Для одного и того же события не следует создавать дублирующие случаи.
- Закрытый случай нельзя повторно обрабатывать без специальной операции.

### 6.2. Агрегат RebookingProposal

**RebookingProposal** представляет предложение альтернативного варианта корректировки путешествия.

Основные данные:
- Идентификатор предложения.
- Идентификатор случая нарушения.
- Список альтернативных рейсов.
- Статус предложения.
- Дата создания.
- Срок действия.

Основные операции:
- формирование предложения;
- добавление альтернатив;
- выбор пользователем варианта;
- отклонение предложения;
- истечение срока действия.

Бизнес-правила:
- Предложение должно быть связано с существующим случаем нарушения.
- Альтернативные рейсы должны соответствовать ограничениям маршрута.
- Пользователь может выбрать только один вариант из актуального предложения.
- Истёкшее предложение нельзя принять.

Выбор предложения не означает автоматического перебронирования билета. Система фиксирует выбор пользователя и инициирует корректировку маршрута в Trip Management.

### 6.3. Уведомления

На текущем этапе отправка уведомлений рассматривается как функциональность Travel Recovery и не выделяется в самостоятельный агрегат.

## 7. Взаимодействие Bounded Contexts

Контексты TravelTech взаимодействуют друг с другом для выполнения основных бизнес-сценариев системы.

### 7.1. Identity и остальные контексты

Identity отвечает за аутентификацию пользователей и выдачу JWT-токенов.

Остальные контексты используют JWT для проверки подлинности пользователя и определения его прав доступа.

Identity не хранит информацию о путешествиях, маршрутах и авиарейсах.

### 7.2. Trip Management и Flight Information

Trip Management обращается к Flight Information для получения сведений об авиарейсах и аэропортах.

Flight Information предоставляет информацию о рейсах, а Trip Management использует её при формировании маршрутов и добавлении бронирований.

### 7.3. Trip Management и Flight Monitoring

При добавлении авиарейса в путешествие Trip Management инициирует запуск его мониторинга.

Flight Monitoring получает идентификатор рейса и начинает отслеживать изменения его статуса.

### 7.4. Flight Monitoring и Flight Information

Flight Monitoring получает сведения об авиарейсах через Flight Information.

Flight Information отвечает за получение и хранение данных о рейсах, а Flight Monitoring — за анализ изменений и обнаружение нарушений расписания.

### 7.5. Flight Monitoring и Travel Recovery

При обнаружении задержки или отмены рейса Flight Monitoring формирует событие, например FlightCancelled или FlightDelayed.

Travel Recovery получает событие и запускает обработку возникшей проблемы.

### 7.6. Travel Recovery и Trip Management

Travel Recovery получает от Trip Management информацию о путешествиях, затронутых изменением статуса рейса.

После поиска альтернатив и выбора пользователем подходящего варианта Travel Recovery инициирует изменение маршрута через Trip Management.

Trip Management самостоятельно проверяет допустимость изменения и сохраняет обновлённый маршрут.

## 8. Способы взаимодействия между контекстами

Для взаимодействия микросервисов TravelTech используются REST, gRPC и RabbitMQ.

### 8.1. REST

REST используется для синхронного взаимодействия через HTTP API.

Основные сценарии:
- получение информации об авиарейсах;
- получение информации о путешествиях;
- управление путешествиями и бронированиями;
- взаимодействие клиентского приложения с микросервисами.

### 8.2. gRPC

gRPC используется для внутреннего синхронного взаимодействия между микросервисами.

Обмен данными осуществляется с использованием Protocol Buffers. Контракты взаимодействия описываются в файлах `.proto`.

Предполагаемый сценарий:
- Trip Management обращается к Flight Information для получения структурированной информации об авиарейсе.

### 8.3. RabbitMQ

RabbitMQ используется для асинхронного обмена командами и событиями между микросервисами.

Основные сценарии:
- Trip Management отправляет команду StartFlightMonitoring для запуска мониторинга рейса.
- Flight Monitoring публикует события FlightCancelled и FlightDelayed при обнаружении изменений.
- Travel Recovery получает события о нарушениях и запускает их обработку.
- Travel Recovery отправляет команду RouteChangeRequested после выбора пользователем альтернативного варианта.

Асинхронное взаимодействие позволяет сервисам обрабатывать сообщения независимо друг от друга.

Для повышения надёжности обмена сообщениями в дальнейшем планируется использовать Transaction Outbox, повторную обработку и защиту от дублирования сообщений.
