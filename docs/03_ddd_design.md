# DDD Design

## 1. Bounded Contexts

В системе TravelTech выделено пять ограниченных контекстов (Bounded Contexts):

1. **Identity** — управление пользователями и авторизацией.
2. **Trip Management** — управление путешествиями, маршрутами и бронированиями.
3. **Flight Information** — хранение информации об авиарейсах и аэропортах.
4. **Flight Monitoring** — мониторинг рейсов и хранение истории изменения их статусов.
5. **Travel Recovery** — обработка нарушений расписания и подготовка предложений по корректировке путешествий.

### 1.1. Состав контекстов и агрегатов

| Контекст | Агрегаты и сущности |
|---|---|
| Identity | User, Role, RefreshSession |
| Trip Management | Trip, ItinerarySegment, Booking |
| Flight Information | Airport, Flight |
| Flight Monitoring | FlightMonitoring, FlightStatus |
| Travel Recovery | DisruptionCase, RebookingProposal |

В Trip Management дополнительно реализована техническая модель `OutboxEvent`, используемая для паттерна Transactional Outbox.

## 2. Identity Context

**Назначение:** управление учётными записями пользователей, ролями и сессиями авторизации.

### 2.1. User

Представляет зарегистрированного пользователя системы.

Основные данные:
- Идентификатор пользователя.
- Email.
- Имя пользователя (username).
- Хеш пароля.
- Идентификатор роли.
- Дата регистрации.

Связь: каждый пользователь связан с одной ролью через `role_id`.

### 2.2. Role

Представляет роль пользователя в системе.

Основные данные:
- Идентификатор роли.
- Название роли.

Одна роль может быть назначена нескольким пользователям.

### 2.3. RefreshSession

Представляет сессию обновления авторизации.

Основные данные:
- Идентификатор сессии.
- Идентификатор пользователя.
- Хеш refresh-токена.
- Срок действия.
- Дата создания.

Каждая сессия связана с конкретным пользователем.

### 2.4. Бизнес-правила

- Email пользователя должен быть уникальным.
- Имя пользователя должно быть уникальным.
- Пароль хранится в виде хеша.
- Пользователь должен иметь назначенную роль.
- Refresh-токен хранится в виде хеша и должен быть уникальным.

## 3. Trip Management Context

**Назначение:** управление путешествиями пользователей, их маршрутами и бронированиями.

### 3.1. Trip

`Trip` — корневая сущность агрегата путешествия.

Основные данные:
- Идентификатор путешествия.
- Идентификатор владельца.
- Название.
- Дата начала.
- Дата окончания.
- Статус.
- Дата создания.

Связанные сущности:
- `ItinerarySegment` — этапы маршрута.
- `Booking` — бронирования, относящиеся к путешествию.

Обе сущности связаны с Trip через `trip_id`. При удалении путешествия связанные этапы маршрута и бронирования также удаляются.

### 3.2. ItinerarySegment

Представляет отдельный этап маршрута путешествия.

Основные данные:
- Идентификатор этапа.
- Идентификатор путешествия.
- Идентификатор авиарейса.
- Код аэропорта отправления.
- Код аэропорта прибытия.
- Время отправления.
- Время прибытия.
- Позиция этапа в маршруте.

`ItinerarySegment` является дочерней сущностью Trip, а не самостоятельным агрегатом.

Порядок этапов определяется полем `position`.

### 3.3. Booking

Представляет информацию о бронировании, связанном с путешествием.

Основные данные:
- Идентификатор бронирования.
- Идентификатор путешествия.
- Идентификатор авиарейса.
- Код бронирования.
- Номер билета (необязательный).
- Статус бронирования.
- Дата создания.

Каждое бронирование связано с одним путешествием.

TravelTech хранит информацию о бронированиях, но не выполняет покупку билетов и оплату.

### 3.4. OutboxEvent

`OutboxEvent` — техническая модель, используемая для реализации Transactional Outbox.

Основные данные:
- Идентификатор события.
- Тип события.
- Полезная нагрузка (payload).
- Дата создания.
- Дата обработки.

Событие сохраняется в базе данных Trip Service в рамках транзакции вместе с бизнес-изменениями. После этого отдельный процесс публикует его в RabbitMQ.

OutboxEvent не является частью бизнес-агрегата Trip.

## 4. Flight Information Context

**Назначение:** хранение и предоставление информации об авиарейсах и аэропортах.

### 4.1. Airport

Представляет аэропорт, используемый при описании авиарейсов.

Основные данные:
- Идентификатор аэропорта.
- Код IATA.
- Название.
- Город.
- Страна.

Код IATA является уникальным.

Один аэропорт может быть связан с несколькими рейсами как аэропорт отправления или прибытия.

### 4.2. Flight

Представляет информацию об авиарейсе.

Основные данные:
- Идентификатор рейса.
- Номер рейса.
- Авиакомпания.
- Идентификатор аэропорта отправления.
- Идентификатор аэропорта прибытия.
- Плановое время отправления.
- Плановое время прибытия.
- Дата создания.

Flight связан с двумя объектами Airport:
- аэропортом отправления;
- аэропортом прибытия.

Для хранения этих связей используются `departure_airport_id` и `arrival_airport_id`.

## 5. Flight Monitoring Context

**Назначение:** управление мониторингом авиарейсов и хранение истории изменения их статусов.

### 5.1. FlightMonitoring

Представляет процесс мониторинга конкретного авиарейса.

Основные данные:
- Идентификатор мониторинга.
- Идентификатор авиарейса.
- Статус мониторинга.
- Время последней проверки.
- Дата создания.

Для одного авиарейса предусмотрена одна запись мониторинга: поле `flight_id` имеет ограничение уникальности.

### 5.2. FlightStatus

Представляет запись о состоянии авиарейса в определённый момент времени.

Основные данные:
- Идентификатор записи.
- Идентификатор мониторинга.
- Статус рейса.
- Описание состояния.
- Время фиксации.

Каждая запись FlightStatus связана с конкретным FlightMonitoring.

Один объект мониторинга может содержать несколько записей истории статусов.

При удалении записи мониторинга связанные записи истории также удаляются.

## 6. Travel Recovery Context

**Назначение:** обработка нарушений расписания авиарейсов и подготовка предложений по корректировке путешествий.

### 6.1. DisruptionCase

Представляет случай нарушения первоначального плана путешествия.

Основные данные:
- Идентификатор случая.
- Идентификатор путешествия.
- Идентификатор проблемного авиарейса.
- Тип нарушения.
- Описание проблемы.
- Статус обработки.
- Дата создания.

Один случай нарушения может содержать несколько предложений по изменению маршрута.

### 6.2. RebookingProposal

Представляет предложение альтернативного варианта корректировки путешествия.

Основные данные:
- Идентификатор предложения.
- Идентификатор случая нарушения.
- Идентификатор альтернативного авиарейса.
- Статус предложения.
- Описание.
- Дата создания.

Каждое предложение связано с одним DisruptionCase.

При удалении случая нарушения связанные предложения также удаляются.

Предложение альтернативного рейса само по себе не означает автоматического бронирования или покупки билета.

## 7. Взаимодействие Bounded Contexts

Контексты взаимодействуют друг с другом через API и механизмы обмена сообщениями. Прямой доступ к таблицам других микросервисов не используется.

### 7.1. Identity и остальные контексты

Identity отвечает за аутентификацию и выдачу JWT-токенов.

Остальные микросервисы используют токены для проверки доступа к защищённым операциям.

### 7.2. Trip Management и Flight Information

Trip Management хранит идентификаторы авиарейсов и коды аэропортов в этапах маршрута и бронированиях.

Flight Information отвечает за хранение сведений об авиарейсах и аэропортах.

### 7.3. Flight Information и Flight Monitoring

Flight Service и Flight Monitoring Service взаимодействуют синхронно с использованием gRPC.

Контракт взаимодействия описан в файле `flight.proto`.

### 7.4. Trip Management и RabbitMQ

Trip Management сохраняет события в Outbox и публикует их через RabbitMQ.

Это позволяет передавать информацию другим компонентам без необходимости выполнять синхронный вызов в рамках каждой бизнес-операции.

### 7.5. Travel Recovery и Trip Management

Recovery Service координирует процесс восстановления путешествия.

Для выполнения операций с путешествием он взаимодействует с Trip Service через API. В рамках распределённого процесса используется Saga Orchestration.

## 8. Основные DDD-принципы

При проектировании TravelTech используются следующие принципы Domain-Driven Design:

- **Bounded Context** — разделение предметной области на пять независимых контекстов.
- **Aggregate** — группировка связанных сущностей вокруг корневой сущности.
- **Aggregate Root** — объект, через который выполняется управление состоянием агрегата.
- **Repository** — абстракция для доступа к данным.
- **Ubiquitous Language** — использование единых терминов предметной области в документации и коде.
- **Database per Service** — независимое владение данными каждым микросервисом.
