# Проектирование баз данных

В проекте используется PostgreSQL. Каждый микросервис работает со своей отдельной базой данных. Такой подход позволяет сервисам независимо управлять своими данными.

## 1. Identity Service — `identity_db`

База данных хранит пользователей, их роли и сессии обновления токенов.

| Таблица | Назначение |
|---|---|
| `users` | Данные пользователей: email, имя пользователя, хеш пароля и роль |
| `roles` | Роли пользователей |
| `refresh_sessions` | Хеши refresh-токенов и сроки их действия |

Связи:
- Один пользователь связан с одной ролью.
- Одна роль может быть назначена нескольким пользователям.
- У одного пользователя может быть несколько refresh-сессий.

## 2. Trip Service — `trip_db`

База данных хранит информацию о путешествиях, маршрутах, бронированиях и событиях для последующей публикации в RabbitMQ.

| Таблица | Назначение |
|---|---|
| `trips` | Основная информация о путешествии: владелец, название, даты и статус |
| `itinerary_segments` | Сегменты маршрута: рейс, аэропорты, время вылета и прилёта, позиция в маршруте |
| `bookings` | Информация о бронированиях: номер бронирования, номер билета, статус и идентификатор рейса |
| `outbox_events` | События, сохранённые для последующей отправки в RabbitMQ |

Связи:
- Одно путешествие может содержать несколько сегментов маршрута.
- Одно путешествие может содержать несколько бронирований.
- Сегменты маршрута и бронирования связаны с путешествием через `trip_id`.

## 3. Flight Service — `flight_db`

База данных хранит справочную информацию об аэропортах и рейсах.

| Таблица | Назначение |
|---|---|
| `airports` | Данные аэропортов: IATA-код, название, город и страна |
| `flights` | Данные рейсов: номер, авиакомпания, аэропорты отправления и прибытия, время вылета и прилёта |

Связи:
- Один аэропорт может быть аэропортом отправления для нескольких рейсов.
- Один аэропорт может быть аэропортом прибытия для нескольких рейсов.
- Каждый рейс связан с аэропортами отправления и прибытия.

## 4. Flight Monitoring Service — `monitoring_db`

База данных хранит текущий статус отслеживания рейсов и историю его изменений.

| Таблица | Назначение |
|---|---|
| `flight_monitoring` | Информация об отслеживании рейса, его текущий статус и время последней проверки |
| `flight_statuses` | История изменения статусов рейса с описанием и временем фиксации |

Связи:
- Одна запись отслеживания может содержать несколько записей истории статусов.
- Каждая запись истории связана с записью отслеживания через `monitoring_id`.
- Для одного рейса предусмотрена одна запись отслеживания.

## 5. Recovery Service — `recovery_db`

База данных хранит информацию о нарушениях в поездках и предложениях по восстановлению маршрута.

| Таблица | Назначение |
|---|---|
| `disruption_cases` | Случаи нарушения поездки: идентификаторы поездки и рейса, тип нарушения, описание и статус |
| `rebooking_proposals` | Предложения альтернативных рейсов и их статусы |

Связи:
- Один случай нарушения может содержать несколько предложений по перебронированию.
- Каждое предложение связано со случаем нарушения через `disruption_case_id`.

## Особенности хранения данных

- Каждый микросервис самостоятельно управляет своей базой данных.
- Связи между таблицами внутри одной базы данных реализованы с помощью внешних ключей.
- При взаимодействии между микросервисами используются идентификаторы сущностей (UUID). Например, `flight_id` в Trip Service ссылается на рейс из Flight Service, но не является внешним ключом в базе данных.
- События для асинхронного взаимодействия сохраняются в таблице `outbox_events` в рамках Transactional Outbox.
